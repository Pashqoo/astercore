# Правила работы в Astercore

Перед работой прочитать `.cursor/rules/assistant.mdc` и `.cursor/rules/memory.md`. Соблюдать
правила из них и тематических файлов памяти, относящихся к задаче (`protocol.mdc` — wire-контракт
терминала, `aster.mdc` — репозиторий и решения, `trading.mdc` — торговля).

**В `trading.mdc` два слоя, и путать их нельзя:** раздел «Aster: механика биржи» проверен
замерами, всё остальное помечено `ПЕРЕНЕСЕНО` — это семантика MoonBot из TInvestCore, на Aster
ещё не проверявшаяся. Снимать пометку только после живой проверки, по одной секции.

Ядро Aster для MoonTerminal по MoonProto. Постановка, замеры и вехи — `PLAN.md`; его читать первым.

Соседний проект `../TInvestCore` — то ядро, из которого это адаптировано. **Его не править ни одной
строкой**, читать можно и нужно: `src/server/` в обоих репозиториях держится текстуально близко
специально, чтобы починка кодека переносилась между ядрами диффом.

`../moon-terminal` — чужой проект, править нельзя. Из него читаются только факты о том, как
терминал понимает ядро (`crates/moon-core/src/venue.rs`, `symbol/mod.rs`, `market/source/read.rs`).

## Commands

Разработка на Mac, `cargo` в `~/.cargo/bin`: `export PATH="$HOME/.cargo/bin:$PATH"`.
Проверено 01.10 — каждая из этих команд прогнана.

- build: `cargo build --release -p aster-core --all-targets`
- test: `cargo test -p aster-core --all-targets` и `cargo test -p moonproto --lib -- server::`
  — наша часть вендора. Без второй команды правка в `server/codec/` проверяется только через ядро.
  Клиентские тесты апстрима (`client::tests::service_cmd_tests`) падают пачкой из-за общего
  состояния между тестами — поодиночке зелёные, дерево не наше, не чиним.
- lint: `cargo clippy -p aster-core --all-targets --no-deps -- -D warnings`
- format: `rustfmt --edition 2021` изменённых файлов в `crates/aster-core` и
  `crates/moonproto/src/server/`. Один прогон **перед** сборкой, не хуком на каждую правку.
- vendor check: `tools/check-vendor.sh` — обязательно после любой правки в `crates/moonproto/`.
  Инвариант: от апстрима на `MOONPROTO_REV` отличаются **только** `src/server/**` и две строки
  хука в `src/lib.rs`. Хук стоит **внутри блока `pub mod`, сразу после `pub mod time;`, без пустой
  строки** — это не вкусовщина: allow-list скрипта сопоставляет ровно эти две строки, и пустая
  строка рядом валит проверку на чистом дереве (поймано 01.10).
- vendor sync: `tools/sync-moonproto.sh` — по умолчанию upstream HEAD (решение трейдера: всегда
  последняя версия), явный rev — первым аргументом. Перед первой сборкой нового rev — leak-review дельты.

### Вендорный rev — всегда последний

Решение трейдера 01.10 (`PLAN.md`, «Открытые решения» п. 7). `MOONPROTO_REV` = `9fd0490…`
(28.09, upstream HEAD; терминал на main пинит `87c1725`, разница — только docs). TInvestCore
остался на `2e67562f`: `src/server/` больше не на общем rev, и перенос починки кодека между ядрами
диффом теперь проверяется сборкой, а не предполагается.

## Secrets

- `asterkey*` — ключи API биржи (`.gitignore` закрывает `asterkey*`, `*.key`, `*secret*`, `*.env`).
  **Содержимое этих файлов не читать и не печатать**, в журнал не выводить. Имя `asterkey` не
  покрывалось шаблоном `*.key` — дыра закрыта 01.10, до того как в файл что-то положили.
  С 01.10 в файле лежат **тестовые** ключи, боевые трейдер создаст ближе к деплою. Смена ключей
  кода не меняет. Схема подписи по ним выяснена — **v3, EIP-712** (адрес API-кошелька + приватный
  ключ EVM), `PLAN.md`, «Открытые решения» п. 1.
- `aster-core.key` (появится в M0) — ключ подключения терминала к ядру: `master_key` + `mac_key`.
  Это секрет: кто его имеет, тот торгует этим счётом. Права 600, генерируется ядром.
- `data/config.json` (M4, создаётся ядром на первом старте) — внутри токен телеграм-бота и пароль
  страницы. Права 600 (ослабленные права ядро затягивает при чтении), в журнал не попадает; на
  странице токен и пароль видны только как «задан / не задан».
- `logs/YYYY-MM-DD.log` (M4) — журнал по дням часов трейдера (MSK). Ключ терминала в журнал не
  пишется (только в stdout), подписи и ключи биржи — нигде.
- Подпись запросов (`aster/sign.rs`, M2) — единственное место, где секрет превращается в заголовок
  или в подпись. Ни ключ, ни секрет, ни подпись не логируются ни на одном уровне.
- `listenKey` (M2, user-стрим) — не торгует, но открывает чтение ордеров и денег счёта. Живёт
  только в памяти потоков `aster-account`/`aster-user` и в URL сессии; в журнал не выводится.
- Плейнтекст ключей легитимно живёт только в памяти процесса между чтением файла и формированием
  запроса. Наружу уходит либо `X-MBX-APIKEY` (v1), либо EIP-712-подпись (v3) — сам секрет никогда.

## Канал наблюдения (§7)

Верификация у GUI-ядра не бывает «по коду». Что есть сейчас и чем пользоваться:

1. **`./target/release/aster-core`** — ядро: печатает в stdout ключ (две строки, читать только с
   консоли), `clock:`, `limits:`, `catalog:`, `wire:` и `account:` по живой бирже, дальше **служит
   по UDP** до сигнала. `account:` — первое чтение счёта: подписанные `GET /fapi/v3/balance` +
   `/fapi/v3/positionRisk` клиентом сети подписанта со своей сверкой часов (сеть, сокращённые
   адреса подписанта и счёта, поправка часов, USDT free/equity, открытые позиции `символ
   размер@вход`). Дальше поток `aster-account` перечитывает счёт раз в 15 с и шлёт терминалу
   `TBalanceFull` при каждом изменении; отказы — `account:` в журнале, через 60 с сплошных
   отказов снимок снимается (терминал видит пустой баланс), часы сверяются раз в 10 минут и
   после каждого отказа. Между периодами счёт перечитывается сразу по событию user-стрима
   (поток `aster-user`, `/ws/<listenKey>`; ключ — подписанный `POST /fapi/v3/listenKey` раз в
   30 мин в потоке счёта): в журнале `user: stream open on mainnet (session N)`, на события —
   `account: update (<причина>)` и `order: символ id сторона тип исполнение/статус кол@цена
   filled … client …`. В строке `streams:` этого потока нет. Видно клиентом: `--example balance_snapshot -- "$KEY" 127.0.0.1:3101`.
   Файл ключа — `ASTER_API_KEY_FILE`, по умолчанию `asterkey` в
   рабочем каталоге, сеть — `ASTER_NET` (`mainnet` по умолчанию / `testnet`). Нет файла с именем по
   умолчанию — ядро только маркет-даты (`account: none`); явно названного файла нет, ключ не
   разбирается или биржа отказала — выход с ошибкой. Ключ читается группой или остальными — предупреждение. Остальные строки старта (`tickers:`, `premiumIndex:`, `bookTicker:`, `usage:`,
   `serving`) идут в журнал на stderr, и туда же раз в 5 минут — `streams:` (каждая WS-сессия:
   `trades#0..2`, `marks`, жива ли, сколько сессий открыла) и `load:` (наборы подписок книг и
   свечей, переоткрытые чанки, потерянные книги). Через ~45 с после старта — `warmup:` (свечи 5m
   скринера, сколько рынков и отказов), на каждый ответ `RequestCandlesData` — `candles:` (рынки,
   свечи, чанки, байты, мс сборки). Запускать **не в репозитории**: в рабочем каталоге
   создаётся `aster-core.key`. Порт из `ASTER_CORE_PORT` (по умолчанию 3101), адрес для нового
   ключа — `ASTER_CORE_ADDR`, уровень журнала — `ASTER_CORE_LOG`.
2. **Вендорные примеры как терминал.** К живому ядру подключается `MoonClient` того же rev:
   `KEY=$(sed -n 2p core.out); cargo run --release -p moonproto --example list_markets -- "$KEY"
   127.0.0.1:3101` (каталог), `--example market_refresh` (ряды цен, `prices updated: N`),
   `--example query_hedge_mode`. Это и есть «терминал дошёл до Ready» без GUI. Маркет-дата (M1):
   `--example trades_stream -- "$KEY" 127.0.0.1:3101 BTCUSDT 15` (лента, `[retained-trade]`),
   `--example order_book_stream -- … BTCUSDT 6` (`[book] … full=true`), `--example history_bars --
   … BTCUSDT 5m` (CoinCard, `1500 candles`). Свечи скринера вендорным примером не видны: пробный
   клиент (подписка на ленту → событие `CandlesSnapshot` → `candle_volumes`) собирается отдельным
   крейтом в скрэтчпаде с `moonproto = { path = … }`, в репозиторий не кладётся. Клиент на `disconnect` не шлёт `SessionClose`: ядро
   узнаёт об уходе через 60 с тишины, и только тогда освобождает его подписки.
3. **Перекрёстный замер.** Любое число из `catalog:` сходится с независимым разбором
   `/fapi/v1/exchangeInfo` (питон в скрэтчпаде): **596 USDT-перпов + 0 неперпетуальных + 17 по
   квоте = 613**. Ноль во втором слагаемом — не опечатка: дат-фьючерсов у Aster нет вовсе, а пять
   символов с пустым `contractType` — это пять пред-листингов, и они в каталоге. Было «591 + 5»,
   пока пустое значение ошибочно считалось не-перпетуальным. Расхождение здесь — дефект
   отображения, а не «биржа изменилась».
4. **Контрактный тест на loopback** — есть в дереве: `cargo test -p aster-core --test loopback`.
   Поднимает наш сервер с фикстурным каталогом и доводит `moonproto::MoonClient` до `Ready`,
   проверяя то, что увидел бы терминал (имя и код биржи, маска FUTURES, фильтры, планка цены,
   фандинг в процентах, ряды цен, hedge mode), плюс несчастливую ветку — неизвестный метод
   Engine API получает отказ, а не молчание. С M1 там же — подставной фид: лента, стакан, CoinCard
   и новый фандинг доходят до клиента, отказ биржи по REST доходит отказом; `RequestCandlesData`
   держится до конца прогрева и даёт клиенту часовой объём из запечатанных баров. Сети не требует и
   потому прогоняется всегда.
5. **Сам терминал** (M1+): скриншот кадра. Стакан и чарт по коду не выводятся.
6. **Эмулятор** (M3) — заход стратегии при нулевом денежном риске. На Aster это важнее, чем было
   на MOEX: песочницы под боевую подпись у нас может не быть (`PLAN.md`, «Открытые решения» п. 1).
   Ядро без файла ключа ведёт стратегии **только** в эмуляторе (ручной ордер там отказывается) —
   так и проверяется стратегия без денег: тестовое ядро в скрэтчпаде на своём порту
   (`ASTER_CORE_PORT=3111 ASTER_CORE_ADDR=127.0.0.1`) и пробный клиент — отдельный крейт в
   скрэтчпаде с `moonproto = { path = … }`, который приносит стратегию в `InitConfig.initial_strategies`,
   жмёт `strategies().start()` и печатает образы ордеров и строки журнала ядра.
7. **Страница** (M4): `http://127.0.0.1:3102` (`data/config.json` → `web.bind`), статус JSON —
   `curl -H 'X-Astercore: 1' http://127.0.0.1:3102/api/status`, счётчик API — `/api/metrics`
   (заголовки биржи: вес и ордера против лимитов 2400/1200/300), журнал — `/api/log`. Кадр страницы:
   `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new
   --window-size=1400,1800 --virtual-time-budget=5000 --screenshot=<png> http://127.0.0.1:3102/`.
8. **Коды выхода** (M4): 0 — остановка по просьбе (страница, команда терминала, SIGTERM/SIGINT),
   70 — рестарт со страницы, 1 — сбой или остановка, оставившая входы на бирже. Проверка: ядро на
   переднем плане, `curl -X POST -H 'X-Astercore: 1' …/api/restart`, затем `echo $?` (замерено
   02.10: 70; SIGTERM — «signal: stopping» → «exit 0 (stop)»). Юнит — `tools/aster-core.service`.
9. **Telegram** (M4): токен бота и привязка чата PIN-кодом — на странице, вкладка Telegram. Для
   проверки без Telegram — `ASTER_TELEGRAM_API=http://127.0.0.1:<порт>` на заглушку Bot API.

`MIN_NOTIONAL` на всех символах = 5 USDT, значит живая проверка ордера стоит пять долларов.

## Чего здесь нет

Боевого хоста и деплоя — решение трейдера (`PLAN.md`, «Открытые решения» п. 6); юнит для него
готов (`tools/aster-core.service`, рабочий каталог `/opt/aster-core`). С Mac и REST, и
WebSocket доступны напрямую, прокси не нужен (замерено 01.10: `/fapi/v1/time` 0.30 с,
`wss://fstream.asterdex.com` рукопожатие 0.82 с).
